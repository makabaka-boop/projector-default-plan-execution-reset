# 穹幕投影机校准 · 精确路线台

穹幕投影机校准时需要把**全部姿态（1…N）各测量一次**，镜组在姿态之间转动的耗时
**有方向性**（`C[i→j] ≠ C[j→i]`，非对称）。凭经验排序会浪费宝贵的停机窗口。

本工具给出：

1. **编辑与导入台**：维护 `(N+1)×(N+1)` 的非对称费用矩阵，严格校验，坏数据整批拒绝、
   旧计划保留；并可维护可选的**“先于”关系**（姿态 a 必须先于姿态 b 测量），提交前校验
   姿态存在、不可自指、依赖图无环；
2. **校准路线候选集（精确解区域）**：从停放位 `0` 出发，每个姿态恰好访问一次并回到 `0`，
   计划应用后**一次给出按总耗时升序、同费按完整姿态序列字典序升序排列的前三条互异精确路线**，
   逐条显示排名、总耗时与从 `0` 出发回到 `0` 的完整路径；**默认选择首名**，工程师可改选后
   进入执行台。可行路线不足三条时只返回实际数量（无占位、无重复）；带“先于”关系时，
   **规划器只在候选姿态的全部前置都已访问时才扩展状态**，候选即在满足约束的可行路线内排名；
3. **现场执行台**：以**所选候选**为原计划及增量基线；工程师可把**任一未完成姿态**确认为实际
   下一站（随时偏离所选路线），**确认时再次检查前置条件——未满足则拒绝并保留已确认进度**；
   页面累加已发生费用，并**以该姿态为新起点对全部剩余姿态精确重排**（中途重算只在剩余姿态上
   继续遵守依赖，已完成姿态视为满足），给出最短收尾路线、预计完工耗时及相对**所选候选**的
   增量（基线为次优候选时增量允许为负）；已完成姿态立即禁用，不能再次确认。

> 求解器是 **Held–Karp 动态规划**，精确最优——**不是贪心，也不是全排列枚举**。
> 所有计算都在浏览器本地完成；**数据只留在浏览器**（`localStorage`），没有任何后端 API。

## 适用范围与硬性规则

| 项目 | 规则 |
| --- | --- |
| 姿态编号 | `1…N`，`N` 取 **8—18** 的整数；`0` 为停放位 |
| 费用矩阵 | `(N+1) × (N+1)` 方阵，行优先二维数组，`matrix[i][j]` = 从 `i` 转到 `j` 的耗时 |
| 主对角线 | **必须为 0**（编辑器中锁定，不可改） |
| 非对角项 | **1—9999 的整数**（有方向性，不要求对称；小数、负数、缺项等一律拒绝） |
| 整批拒绝 | 任一缺项、越界、形状不符、类型错误 → **整批拒绝并保留旧计划**，错误就地显示 |
| “先于”关系（可选） | `prerequisites: [[a, b], …]`（旧别名 `dependencies`）：姿态 **a 必须先于** 姿态 b；姿态必须存在、**不可自指**、依赖图**必须无环**，重复边去重；非法依赖整批拒绝、旧计划保留 |
| 新旧字段共存 | 迁移期文件可能同时带 `matrix`/`costs` 与 `prerequisites`/`dependencies`：两侧**分别规范化**（去重/排序/逐格），只有**逐项一致**才接受；任一侧损坏或两侧冲突（含“新依赖为空而旧依赖非空”）→ **整批拒绝**，绝不静默优先某一侧，已生效计划、候选选择与执行进度原样保留 |
| 目标 | 从 `0` 出发，每个姿态恰一次，回到 `0`，总耗时最小；带“先于”关系时只在**满足全部前置的可行路线**中取最优 |
| 候选 | 计划应用后一次给出**前 3 条互异精确路线**，按总耗时升序、同费按完整姿态序列字典序升序；不足 3 条只返回实际数量 |
| 并列 | 路线费用相同时，按姿态序列**字典序**排序（在满足约束的可行路线集合内部），首名即字典序最小最优解 |
| 现场执行 | 确认下一站时再次校验前置：**未满足即拒绝、已确认进度保留**；中途重排只对剩余姿态求解，已完成姿态一律视为前置满足 |
| 性能 | **N=18 生成三条候选 < 4 秒**（带 12 条约束同样 < 4 秒；现场每拍单最优重排随剩余数递减，更快） |

支持的 JSON 形态（含数字与数组，工程师可手工编辑或导入）：

```json
{
  "n": 8,
  "matrix": [
    [0, 12, 7, 33],
    [9, 0, 41, 5],
    [7, 38, 0, 11],
    [30, 6, 14, 0]
  ],
  "prerequisites": [[1, 3], [2, 3]]
}
```

上例表示姿态 **1、2 都必须先于姿态 3**（3 是需要基准姿态的测量）；该字段可省略或为空，
省略时与旧版逐项一致。

- `matrix` 也可写成 `costs`；`prerequisites` 也可写成 `dependencies`；**只给任一侧都完全兼容**。
  两套字段**同时存在**时，各自规范化（矩阵逐格、依赖去重并按 `(a,b)` 升序，空数组与缺省同义）后
  **必须逐项一致才视为同一计划**；任何冲突（含 `prerequisites: []` 而 `dependencies` 非空）或一侧损坏
  都整批拒绝并就地指出冲突位置/损坏侧，避免“导入成功→再导出”悄悄丢弃旧字段、改写计划语义；
- 每条关系必须是恰好两个编号的 `[a, b]`（a 先于 b），编号为 `1…N` 的现有姿态，
  **不可自指**；全部边构成的有向图**必须无环**（相互约束如 `1→2` 与 `2→1` 会被拒绝）；
- 也接受**裸二维数组**，此时 `N = 边长 - 1`（无“先于”关系）；
- 文件导入（`.json`）与文本框粘贴等价，先入草稿，**校验通过后点“校验并应用”才生效**；
  编辑台的“先于”关系是**独立草稿**，与已应用计划分离，非法依赖不会污染上次有效计划。

## 算法说明（为什么是精确解，且一次给出前三名）

定义（`src/solver/tsp.ts`），每个状态不再只存单个最优值，而是固定保留 `k=3` 名**不同后缀**
及其子排名：

```
g[mask][i][r] = 从 target[i] 出发，恰好访问 mask 中全部目标（i 不在 mask 内），最后回到 0
               的全部互异后缀中，第 r 名（按总耗时升序、同费按后缀字典序升序）的耗时
g[0][i][0]    = C(target[i] → 0)
g[mask][i]    = 对每个 j ∈ mask 合并候选流
                 C(target[i] → target[j]) + g[mask \\ {j}][j][*]，取前三名
```

答案：对首个姿态 `i` 合并 `C(0 → target[i]) + g[full \\ {i}][i][*]`，取前三名。

- 每个后继 `j` 给出一条已按 `（耗时, 后缀字典序）` 排好序的候选流；不同 `j` 的首姿态不同，
  同一 `j` 的不同子排名对应互异后缀，所以 `(j, 子排名)` 一一对应互异完整序列，**无需去重**，
  也**不靠禁用首选路线中的边反复调用求解器**。
- k 最优引理：父状态的第 `k` 名必来自某条候选流的前 `k` 名，故子状态只存三名即足够。
- **同费字典序 tie-break**：目标按编号升序；同费候选之间首姿态编号小者整序列更小，合并键
  直接取 `（耗时, j, 子排名）`，恢复时沿 `(后继位, 子排名)` 指针确定性回溯，无需保存序列。
- 紧凑存储：耗时 `Int32Array`（每状态 3 槽，无效槽为哨兵），`(后继位, 子排名)` 打包成
  `j*3+r` 存 `Int8Array`（`j ≤ 19`，单字节足够）。
- 时间复杂度 `O(k·m²·2^m)`，空间 `O(k·m·2^m)`；m=18、k=3 约 1400 万个耗时槽，亚秒至一秒级。
- 互异路线总数 `m!` 不足 3 时（小目标数/剩余子集），答案只有实际数量，**无占位、无重复**。
- `solveOptimal` 走同一 DP 核心的 `k=1` 快路径，**恒等于候选首名**，继续服务既有现场
  后缀重排；**现场重排**只是把 `origin` 从 `0` 换成刚确认的姿态、目标集合换成剩余姿态再解一次；
  每一拍得到的后缀都是该状态下的全局最优后缀。
- **“先于”约束如何进入 DP**：前置条件按姿态编号存成位掩码 `preByPose[b]`（第 a 位为 1 表示
  a 先于 b）。在“从 i 出发、还要走 mask”的视角下，已访问集合 = 全部目标 \\ (mask ∪ {i})，
  故后继 j 可扩展当且仅当 `(preByPose[j] & mask) === 0`——j 的前置只要还落在待走集合 mask 中
  就必须让位；执行中途重排时已完成姿态不在剩余目标集合内，其位自然不在 mask，**自动视为满足**。
  该门只剪掉“不可能合法”的扩展，合并键与同费字典序 tie-break 不变，故排序规则在可行集合内
  与无约束时完全一致；无 `prerequisites` 时掩码为 `undefined`，求解循环走零成本原始路径。
  环在计划提交时即被拒绝（DFS 三色法报出环上姿态），求解器对“无可行路线”的防御分支返回空候选
  并标记 `feasible=false`，执行台入口禁用、上次有效计划不被污染。
- 预计完工 = 已发生费用 + 当前精确最短后缀（含返回 `0` 的边）；增量 = 预计完工
  − **所选候选基线**。基线是候选首名（精确最优）时增量恒 `≥ 0`；工程师改选次优候选后，
  初始精确最短后缀严格更短，**增量允许为负**。
- **应用新矩阵时旧候选与工程师的选择一起失效**：候选集对已生效计划引用做记忆化，
  计划替换即重算并把选择重置为首名。

产品代码中**没有**贪心近似，也**没有** `m!` 枚举；全排列枚举只存在于测试基准
（`src/solver/brute.ts` 的 `bruteForceTopK`），用于穷举小样本核对前三名、数量不足与互异性。

## Docker Compose

多阶段 `Dockerfile`：

- `web` 阶段：构建静态产物并用 **nginx** 发布（纯静态，无后端）；
- `verify` 阶段：装依赖后执行 `npm run verify`，**一次性**，退出码即验收结论。

### 发布页面（端口可用 `WEB_PORT` 覆盖）

```bash
# 默认 8080
docker compose up -d --build web
# 打开 http://localhost:8080

# 覆盖端口
WEB_PORT=9000 docker compose up -d --build web
# 或复制 .env.example 为 .env 后修改 WEB_PORT
```

### 一次性验收

```bash
docker compose --profile verify run --rm verify
```

`verify` 挂在 `verify` profile 下，不会随 `docker compose up` 启动，也不会被重启；
跑完穷举核对与 N=18 性能指标后容器退出。

## 数据与隐私

- 已生效计划只写入当前浏览器的 `localStorage`（键 `dome-calibration-plan-v1`），
  含费用矩阵与已校验的“先于”关系；加载时重新校验，损坏数据（含成环依赖）自动回退默认计划。
- 应用本身不发起任何网络请求（无 `fetch` / XHR / WebSocket / 埋点）；
  部署形态是 nginx 静态文件。清空站点数据或点击“恢复默认计划”即可删除本地数据。
